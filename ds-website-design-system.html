Internal spec · v0.2

One design system, every client site.

Derived from a structural audit of three live GHL sites — Wax on Warriors, San Mob Detailing, and Kleen Car Care. The three sites are ~90% the same layout wearing different skins. This document standardizes that pattern so agents can assemble sites from a component library and page recipes instead of cloning templates.

02Page taxonomy

Every audited site resolves to the same six page types.

Recipe A

Home

Flagship page. Full component sequence, richest copy.

Recipe B

Service page

One per service. Packages, process, add-ons, FAQ. 4–12 per client.

Recipe C

Location page

One per service area. The SEO multiplier — 6–9+ per client, thin but hyper-local.

Recipe D

Utility

About, FAQs, Get Quote, Booking, Blog index.

Recipe E

Legal

Privacy Policy, Terms of Service. Boilerplate with variables.

Recipe F

Special modules

Optional one-offs: certification page (WoW RUPES), Maintenance Club. Recipe variants, not core.

04Global shell

Identical on every page of every site. Driven entirely by site.config — no recipe needed.

TopBar

"Book Your Detail Today" strip + phone number + social icons. Present on all three sites.

Header

Logo · nav (Home, Services ▾, Areas ▾, About, FAQs, Blog, Contact) · phone CTA · Book Today primary CTA. Standardize on dropdowns for both Services and Areas, since counts vary widely (San Mob: 12 services · Kleen: 4).

Footer — fixed 5-column pattern

  • Brand — logo + short positioning blurb
  • Locations We Serve — auto-generated from area list
  • Contact — phone, email, address + "Our Location" blurb
  • Working Hours — per-client schedule string
  • Social + CTA — icons + Book Today button

Below columns: Detailer Systems attribution badge → detailersystems.com, Privacy | ToS links, copyright line All Rights Reserved | Detailer Systems | {Brand} © {Year}.

Config inputs for the shell: brand name, logo, phone, email, address, hours, social links, service list, area list, GTM container ID, theme tokens. Nothing else.

09Data model

Everything an agent needs splits into three layers.

Layer 1

site.config

Global, one per client: brand, logo, contact, address, hours, socials, theme tokens (colors, fonts, radius), GTM ID, service list, area list, booking/quote URLs.

Layer 2

Content collections

services/*.md and areas/*.md with frontmatter: name, slug, hero image, packages, FAQs. Astro auto-generates pages, nav entries, footer links, and sitemap from these — add a city, everything appears.

Layer 3

Generated copy

LLM fills the local-flavor prose fields (intro, "why it matters", location copy) from {city, region, roads, landmarks, climate, demographic angle} inputs.

Booking & quote stay in GHL. The Astro site links out to the existing GHL calendar and form funnels at /booking and /get-quote, so all downstream automations remain untouched.

11Open decisions

1 · Promote "How It Works"? Currently Kleen-only. Recommendation: make it a standard home section — good conversion content, trivial to generate.
2 · Credential module. WoW's RUPES certification page/badge is a one-off. Recommendation: optional module with a badge sub-slot in the About SplitSection.
3 · Reviews/testimonials. None of the three sites have a testimonial component — arguably the biggest conversion gap in the current template. Decide whether to add a standard ReviewsStrip (e.g. Google reviews) to the system.
4 · Location slug format. Standardize on {city}-{st} (Kleen/San Mob). WoW's bare-city slugs would need redirects on migration.

12Architecture — engine & payload

Stack decision: Astro components + CSS variable tokens + content collections is the design system. No shadcn/ui (React runtime + app-UI primitives, wrong problem), no Storybook (replaced by a /styleguide route). Tailwind optional for layout utilities; theme always via tokens.

The mental model: one engine repo holds everything shared — components, layouts, recipes, token plumbing. The payload is everything client-specific — one config file, content markdown, an assets folder. A client site = engine + payload, nothing else. Agents write only to the payload; if anything outside client/ ever needs editing, the engine is missing a feature.

Engine

ds-site-engine (build once)

src/components/ — the 14 components · src/layouts/BaseLayout.astro — shell wired in · src/pages/ — the recipes as code (index.astro, [service].astro, [area].astro, utility, legal, styleguide.astro) · src/styles/tokens.css · content.config.ts — zod schemas · scripts/new-client.ts — payload scaffolder.

Payload

client/ (per client, agent-written)

site.config.ts — brand, contact, hours, socials, GHL booking/quote URLs, GTM ID, theme preset + accent, module flags · content/services/*.md and content/areas/*.md — frontmatter + generated prose · assets/ — fixed naming (hero.jpg, founder.jpg, service-{slug}.jpg).

Key mechanics

  • Recipes contain no content. index.astro is a component sequence fed from config + collections — the recipe spec above, turned into code.
  • Zod validation is the safety net. Malformed agent output fails the build with a named error instead of shipping a broken page.
  • Dynamic routes auto-generate pages. Add a city markdown file → page, nav entry, footer link, and sitemap entry appear.
  • Booking & quote stay in GHL. /booking and /get-quote link out to existing GHL funnels; downstream automations untouched.

New-client workflow

  • 1 · Create client repo from the engine (GitHub template repo)
  • 2 · Agent pipeline fills client/: intake data → config · service/area lists → skeleton markdown · LLM pass fills prose fields · photos in
  • 3 · Build — zod + link check passes or tells the agent exactly what to fix
  • 4 · Deploy (Cloudflare Pages/Netlify), point domain, add GTM
Update propagation strategy. Start with copy-forward (fixes reach new clients only; existing sites frozen — fine at 3–20 clients). Add an engine→client sync script when the pain appears (no merge conflicts by construction, since clients never touch src/). Consider npm-package engine only at 50+ sites. The client/-only rule preserves the ability to migrate between models later.

13Design layers & presets

Principle: agents make selections, not decisions. Free-form token freedom produces drift; every design output must be a combination a human approved.

Layer 1

Tokens — 80% of differentiation

Color, font pair, radius, surface treatment. The audit proved layouts can be identical while sites read as different businesses. Every valid token combo is safe by design.

Layer 2

Variants — small enums, earned

~5–8 decisions site-wide: Hero: image|video, ServicesGrid: tiles|cards, imageSide (auto-alternated), module flags. New variants enter the engine as reviewed options — never agent improvisation.

Layer 3

Photos & copy — agent territory

Local prose, headline angles, client photography. Content freedom inside fixed slots — this is what makes sites feel custom.

Brand presets (agents never touch raw tokens)

4–6 human-curated token bundles, each a complete tested combination with a personality label. Agent's design job collapses to one classification: logo + positioning → preset, plus accentColor from the logo (contrast-validated — the only raw value it sets).

PresetFeelFits
stealthNear-black, sharp corners, condensed displayPerformance / ceramic-coating brands
freshWhite/teal, soft radius, clean grotesqueFamily / eco-friendly positioning
chromeDark blue/silver, metallic accentsPremium / luxury detailers
boldHigh-saturation accent, heavy display faceYoung hustle brands
QA loop: the /styleguide route renders every component under the active preset — per-client visual QA is one page. Known trade-off: sites are recognizable siblings to a trained eye; acceptable for local-service SEO, and bespoke design is a separate paid engagement outside the engine.

14Implementation roadmap
